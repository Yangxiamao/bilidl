# 在线播放加速：把多线程分段用在 B 站网页播放器上

> **旧方案，已删除。** 这一页记录的是 v1.0.x 里「插件 DNR 重定向 + bilidl-web 本地代理（`/play/`、`bilidl_play.py`）」的设计和实测。v1.1.0 起它被纯插件的播放加速（已拆到 bilifast 仓库，见 [PLAY_EXTENSION.md](https://github.com/Yangxiamao/bilifast/blob/main/docs/PLAY_EXTENSION.md)）替代，相关代码和 `tests/play_test.py`、`tests/play_bench.py` 都已删除，要看可以在 git 历史里找（v1.0.1）。这里的节点实测和播放器取数方式仍可参考。

## 结论
B 站网页播放器卡顿，根子和下载慢是同一个：**CDN 对每个连接单独限速**。播放器的所有视频分段请求都走**同一条 HTTP/2 连接**，而且 API 默认给的节点（`mirrorcosov`）常常只有零点几 MB/s。4K 的平均码率约 2 MB/s，2 倍速就要 4 MB/s，单连接根本跟不上。

做法：Chrome 插件用 declarativeNetRequest 把播放器对 `upos-*` 节点的 `.m4s` 请求重定向到本机 bilidl-web 的 `/play/<原始链接>`。bilidl-web 把请求拆成 1 MB 的块，用 16 + 4 个线程从实测最快的节点并发拉取，再按顺序流式回给播放器；同时按播放器的实际取数速度预读约 90 秒。画面、弹幕、评论、清晰度切换都还是 B 站自己的。

模拟 4K 播放（1x → 2x → 跳到 60% → 3x）：直连时每个阶段都卡 2~7 次、累计卡十几到二十几秒；经代理后四个阶段**都没有卡顿**。

## 第 0 步实测（2026-10-27，作者的网络）

### 节点
- playurl 给的节点是 `upos-sz-mirrorcosov.bilivideo.com`（baseUrl）和 `upos-hz-mirrorakam.akamaized.net`（backupUrl），带 `ov` 的是海外节点；没有出现 PCDN（`*.mcdn.bilivideo.cn`）。
- **`upos-sz-mirror08c` 已经解析不到了**（10-14 测的时候还是最快的），`mirrorhwov`、`mirror08h` 也解析不到。写死的节点列表会过时。
- 单连接 / 8 线程吞吐（MB/s，每线程连续请求 1 MB Range，测 5 秒）：

| 节点 | x1 | x8 |
|---|---|---|
| mirrorhwb | 1.30 | 10.9 |
| mirror08ct（和 mirrorhw 解析到同一组 IP） | 1.26 | 10.0 |
| mirrorhw | 1.21 | 9.6 |
| mirroralib | 1.02 | 9.0 |
| mirroraliov | 0.75 | 6.4 |
| mirrorcosov（API 默认） | 0.68 | 3.7，有超时 |
| akamai（API 备用） | 0.95 | **0.96**：总带宽封顶，加线程不涨 |
| mirrorali / cos / cosb / bos / estgoss | 0.2~0.4 | 1.1~1.9 |
| mirrorbd | 0 | – |
| mirrorcf1ov | HTTP 570 | – |

- 同一节点前后几分钟能差好几倍：mirroralib 一次 x8 是 9.0，另一次 x16 只有 2.1；mirror08ct 一次 x8 是 10.0，另一次 x16 是 18.6。所以**节点必须按运行时实测的速度挑**，不能写死顺序。
- akamai 的链接也带 `upsig`，**把域名换成 upos 节点照样有效**（多出来的 `hdnts` 参数会被忽略）。SPEEDUP.md 里「akamaized 签名方式不同、不要换域名」的说法现在不成立了。

### 播放器怎么取数据（无头 Chrome + CDP 记录网络请求）
- 视频和音频分段都是在 **Worker 里用 XHR** 发的（2026-10-29 再测时已经改成主线程 XHR，见 [EXTENSION_ONLY.md](https://github.com/Yangxiamao/bilifast/blob/main/docs/EXTENSION_ONLY.md)；DNR 重定向不受影响），带 `Range: bytes=a-b` 请求头，一个请求一个 DASH 分段（360P 视频约 100~250 KB，音频约 30 KB），先取 `bytes=0-xxx` 的初始化段和 sidx。
- **全部请求复用一条 HTTP/2 连接**，所以整个播放器只有一条连接的带宽。
- 播放器自己最多缓冲到领先播放位置约 **72 秒**，2 倍速时也是 72 秒（墙上时间只剩 36 秒）。
- cosov 偶尔一个分段几秒没响应，播放器报 `Fragment Loaded Error` 后换到 akamai 重试，再换回 cosov。

### Chrome 的「本地网络访问」（LNA）
- Chrome 156 上，bilibili.com 的请求被扩展重定向到 `http://127.0.0.1` 时，**要用户授权「本地网络访问」**。没授权时请求直接失败（`LocalNetworkAccessPermissionDenied`），视频完全放不出来（停在 0 秒）。
- 授权后（CDP 的权限名是 `local-network-access`）完全正常：46 个分段全部 206，缓冲照常涨到 72 秒。
- 跨源重定向后，请求的 `Origin` 是 `null`；Range 是 CORS 安全请求头，没有发预检（OPTIONS）。
- 所以**不能无条件重定向**：插件先从页面里 `fetch` 一次 `http://127.0.0.1:8765/play/ping`，成功了才给这个标签页加重定向规则。第一次 fetch 会触发 Chrome 的授权提示。

### 其他坑
- B 站会把 `www.bilibili.com/video/BV…` 跳转到带语言前缀的 `www.bilibili.com/zh-Hans/video/BV…`（至少无头 Chrome 下会），原来插件只匹配 `/video/*`，跳转后内容脚本不注入，连下载按钮也不出现。现在同时匹配 `/*/video/*`。
- 品牌版 Chrome 137 起不支持 `--load-extension`，自动化测试要用 `--remote-debugging-pipe --enable-unsafe-extension-debugging` 加 CDP 的 `Extensions.loadUnpacked`。
- 游客身份看一会儿，B 站会弹登录提示并暂停视频（缓冲是满的，不是卡顿），测试时要分清。

## 设计

### 插件（chrome-extension/）
- `play.js`（`document_start`，视频页、列表页、番剧页，含语言前缀）：每 10 秒 `fetch` 一次 `/play/ping`。通了就请后台为本标签页开启重定向，不通就关闭，并区分原因：等待授权 / 被拒绝 / bilidl 没运行。
- `background.js`：
  - 用**会话规则 + `tabIds`** 按标签页开关，规则 id 就是标签页 id；`regexSubstitution` 把整个原始链接拼到 `/play/` 后面。
  - 用 `webRequest` 盯着重定向过去的请求：连接失败（bilidl 退出）或连续 3 次 5xx，**立刻撤掉这个标签页的规则**，30 秒内不重新打开。只靠 10 秒一次的探测太慢：播放器几秒内重试几次都失败，就会报错并把进度重置到 0（实测遇到过）。
  - `net::ERR_FAILED` 不直接当成 bilidl 退出：它是 Chrome 的通用错误码，bilidl 好好的时候也会出现（2026-10-29 实测：服务一直在跑、没返回过任何错误，插件却因为一次 ERR_FAILED 退回直连）。遇到它时后台先连一下 `/play/ping`，3 秒内连不上才立刻撤掉规则，连得上就和 5xx 一样按连续 3 次计数。
  - bilidl 这边，播放器等一个块超过 10 秒、或者等了 10 秒以上才断开请求时会写日志（「在线播放等待较久」「播放器等了 … 秒后断开了请求」），对照插件面板上的错误时间就能看出是不是节点卡住造成的。
  - `playStatus`：给面板用，带上 `/api/play_stats`。
- `content.js`：面板顶部一行状态「⚡ 播放加速中 · 预读领先 xx 秒 · 节点 xx · x MB/s」，可以关闭/开启（存在 `chrome.storage.local.playAccel`）。

### 代理（bilidl_play.py）
- **资源**：以 URL 路径（如 `/upgcxcode/…/xxx-1-30120.m4s`）为键，和节点、签名无关。每个请求都用它带来的最新链接作为换域名的模板，签名过期由播放器自己刷新，代理不调 playurl。
- **分块**：1 MB 一块，存在内存里。同一块排队或下载中时只有一个任务，后来的请求等同一个任务。
- **两级优先级**：0 = 播放器正在等的块，1 = 预读。一个请求覆盖的几个块一起以优先级 0 排队、并发拉取。另有 4 个线程只拉优先级 0 的块，预读把 16 个普通线程占满时也不用排队。
- **对冲**：播放器在等的块 2.5 秒还没拉完，就同时向另一个节点再拉一份，谁先到用谁。单个连接偶尔会很慢但一直有数据，不会触发超时，没有对冲时 p95 请求耗时有 10~17 秒。对冲用单独的线程，所以即使所有工作线程都被慢节点占住、这个块还没人拉，也照样能对冲。
- **挑节点**（`bilidl.HostHealth`，和下载共用）：每个节点记单连接速度的滑动平均（1 MB 块的字节数 ÷ 耗时；失败时减半，超时减到四分之一），按速度排序。单次拉取 5 秒收不到数据算超时。
  - 预读块：没测过的节点优先，好让每个节点都被试到；之后 85% 在最快的 3 个节点之间随机分，15% 随机分给其余节点，让排名跟得上变化。不全压在最快的一个节点上：实测 cosov 有时单连接最快（约 4 MB/s），但会间歇性卡住几秒，全压上去时所有线程都堵在它的超时上，跳转后每个请求都要等 8 秒。
  - 播放器在等的块：只用测过的最快节点。
  - akamai 不参与排序（单连接测出来不慢，但总带宽封顶，会被误判成快节点），只在第 3 次重试时用。
  - 连续失败 3 次冷却 60 秒，和下载一样。
- **倍速自适应的预读窗口**：窗口 = clamp(播放器最近 20 秒的取数速度 × 90 秒, 32 MB, 256 MB)。取数速度已经包含了码率和倍速，所以 2 倍速时窗口自动翻倍，用别的倍速插件开到 3x、4x 也一样。
  - 刚开始和跳转后的 30 秒里，播放器在补自己 72 秒的缓冲，取数速度偏高，这段时间只按它预读 20 秒（不低于 32 MB）。最早的版本这段时间固定用 32 MB，4K 2 倍速补缓冲时代理只有 2~5 MB/s，补满要近 1 分钟；改了以后 8~21 MB/s，约 35 秒补满。
  - 稳定播放时，如果请求的块还没预读到（比如刚切到更高倍速），窗口下限翻倍。
- **跳转**：请求的块没缓存、而且位置跳出「当前位置 − 2 MB ~ 当前位置 + 窗口」时，作废旧窗口里还没开始的预读（在飞的不打断）。
  - 命中缓存的请求不算跳转。4K 时浏览器的媒体缓冲区装不下 70 秒的数据，播放器会回头再要一遍已经下过的片段（实测从 1847 MB 回到 1688 MB）。以前把这当成跳转，预读窗口和取数速度都清零；现在回头请求直接从内存返回，不计入取数速度，也不把位置往回挪。
- **内存**：所有资源合计约 800 MB（768 MiB）。超出时先丢各资源播放位置之前的块，再整个释放最久没用的资源（30 秒内用过的不动）；闲置 10 分钟整个释放。
- **响应**：206 + `Content-Range`，按块就绪的顺序流式写出。CORS 只放行 `null`（重定向后的 Origin）和 `*.bilibili.com`。目标只允许 `https://upos-*.bilivideo.com` / `upos-*.akamaized.net` 上的 `.m4s`，不带 cookie。
- 统计：`GET /api/play_stats`（要 token），网页界面最下方的「在线播放加速」和插件面板都用它。

## 验收（2026-10-27）

### 正确性：`tests/play_test.py` 全部通过
经代理和直连取同样的 Range 逐字节一致（初始化段、跨块、不对齐、2 MB 跨三块、文件最后 1000 字节、开放区间 `bytes=N-`、超出文件末尾截断、完全超出返回 416），音频一致，只给 akamai 链接时换成 mirrorhw 拉取；8 个并发请求落在同一个没拉过的块上，结果都正确，块没有重复拉取；ping、OPTIONS 预检、CORS、错误 Host、5 种非法目标都按预期拒绝。

### 卡顿：`tests/play_bench.py`
BV1bE41127s6（4K，8.5 GB，平均码率 1.97 MB/s），模拟播放器：一次一个约 2 秒的分段请求，缓冲到 72 秒停，缓冲够 2 秒起播。

| 阶段 | 直连 cosov | 代理（第一版） | 代理（最终） |
|---|---|---|---|
| 1x 25 秒 | 起播 9.5 s，卡 4 次共 5.4 s | 起播 3.1 s，卡 1 次 0.1 s | 起播 2.5 s，**不卡** |
| 切到 2x 30 秒 | 卡 7 次共 23.0 s，只拉到 0.92 MB/s | 卡 2 次共 2.7 s | **不卡** |
| 跳到 60% 后 2x 25 秒 | 起播 16.2 s，卡 2 次共 5.8 s | 起播 2.1 s，卡 1 次 14.9 s | 起播 3.7 s，**不卡** |
| 切到 3x 25 秒 | 卡 4 次共 22.2 s | 不卡 | **不卡** |
| 请求耗时 p95 | 6~8 s | 2~17 s | 1.1~3.3 s |

第一版的问题：一个请求只有第一块是高优先级，其余块要等前一块拉完才排队（串行）；单个慢连接没有对冲。最终版改成一个请求的块一起并发拉取、2.5 秒对冲、4 个专用线程。

### 端到端（无头 Chrome 加载插件，真实 B 站播放器，游客 360P）
- 授权本地网络访问后，m4s 请求全部经 `127.0.0.1` 返回 206，1x 和 2x 播放时缓冲一直保持在约 73 秒。
- 播放中途杀掉 bilidl-web：只有 1 个请求失败，`webRequest` 立刻撤掉规则，之后的请求直连 206，**2x 播放没有中断**。
- bilidl-web 重新启动后 3 秒内重新开启转发，跳转后的请求又全部走代理。
- 不授权时不转发，视频照常直连播放。
- 面板状态能正确显示「⚡ 播放加速中 · 预读领先 … · 节点 … · … MB/s」和「bilidl 没有运行，现在是直连播放」。

## 没做（及原因）
- **把下载也改成按实测速度挑节点**：`HostHealth` 已经记录了速度，但下载有断点续传和多年验证过的行为，这次只更新了 `FAST_HOSTS`（去掉解析不到的 08c 和变慢的 ali），没改下载的挑选逻辑。
- **PCDN（mcdn）链接**：作者的网络下 playurl 没给过，插件也不转发；如果以后出现，需要先验证换域名是否有效。
- **番剧**：插件会在番剧页开启转发（链接格式相同），但没有实测过。
- **写盘缓存**：按需求只在观看时预读到内存，不留盘。
